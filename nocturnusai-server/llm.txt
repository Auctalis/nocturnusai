# Logic Server Manual & API Reference

> **Context for Coding LLMs**: 
> You are an advanced AI agent. You excel at probabilistic text generation but sometimes struggle with **deterministic, multi-step logical reasoning** or maintaining the **state** of a complex system over time. 
> 
> The **NocturnusAI Logic Server** is designed to be your **Symbolic Cortex**. You should offload strict logic, rule-checking, and state validation to this system.
> 
> **Core Directives**:
> 1.  **Do not guess** the state of the world. Query it.
> 2.  **Do not simulate** complex logic in your context window. Assert the rules and let the engine solve it.
> 3.  **Do not hallucinate** database consistency. Use transactions.

---

## Part 1: The Mental Model

To use this system effectively, you must understand how it represents the world.

### 1. The Atom (The Fundamental Unit)
Unlike a SQL database (tables and rows) or a Graph DB (nodes and edges), NocturnusAI uses **Atoms** (Hyperedges). An Atom is a single assertion of truth.

Structure:
-   **Predicate**: The category of the relationship (e.g., `Parent`, `Is_Online`, `Transfer_Valid`).
-   **Arguments**: An ordered list of terms involved in the relationship.
    -   `["Socrates"]` (1-ary)
    -   `["Alice", "Bob"]` (2-ary)
    -   `["Transaction_1", "Alice", "Bob", 50.00]` (4-ary)
-   **Truth Value**: Is this true or false? 
    -   `negated: false` -> The Fact exists. (Positive Assertion)
    -   `negated: true` -> The Fact explicitly *does not* exist or is false. (Negative Assertion)
-   **Scope**: A partitioning key (e.g., `doc_version_1`, `simulation_A`). Two atoms that look identical but have different scopes are **completely different facts**. This allows you to model hypothetical scenarios or distinct documents without data bleeding.

### 2. The Logic Rule (The Brain)
Rules allow the system to *infer* knowledge that hasn't been explicitly asserted.
**Syntax**: `Head(...) <- Body1(...), Body2(...), ...`

-   **Variable Binding**: Variables (starting with `?`) bind values across the rule.
    -   Example: `Grandparent(?x, ?z) <- Parent(?x, ?y), Parent(?y, ?z)`
    -   Logic: "If there exists a person `?y` such that `?x` is parent of `?y` AND `?y` is parent of `?z`, THEN `?x` is grandparent of `?z`."
-   **Unification**: The engine finds all possible values for `?x`, `?y`, and `?z` that satisfy the body, and projects them to the head.

## Part 2: Advanced Theoretical Concepts

### 1. The Frame Problem & Scoping
In AI, the "Frame Problem" is the difficulty of knowing what *doesn't* change when an action occurs. NocturnusAI uses **Scopes** to handle this.
-   **Usage**: Create a new scope for a new "turn" or "simulation step". Copy forward only what persists.
-   **Example**: `scope="Turn_1"` vs `scope="Turn_2"`.

### 2. Monotonicity vs Non-Monotonicity
-   **Monotonic Logic**: Adding new facts never invalidates old conclusions. (e.g., "Socrates is a Man" -> "Socrates is Mortal").
-   **Non-Monotonic Logic (TMS)**: NocturnusAI supports retracting facts. If you retract "Socrates is a Man", the system *automatically withdraws* "Socrates is Mortal". This is crucial for modeling changing worlds (e.g., User logs out -> Session is no longer valid).

### 3. Negation: Explicit vs Failure
-   **Negation as Failure (NAF)**: "If I don't know it, it's false." form.
-   **Explicit Negation**: "I know for a fact it is NOT true."
-   NocturnusAI supports **Explicit Negation** in rules via `negated: true` in body atoms.
-   *Rule*: `Safe to Cross(?x) <- Traffic Light(?x, Green), NOT Traffic Incoming(?x)`

## Part 3: Logic Templates & Reasoning Patterns

You can define rules manually, but the server provides **High-Level Templates** (`/assert/template`) for standard logical forms. Use these to build robust arguments.

### 1. Modus Ponens (Forward Deduction)
**Logic**: If $P \implies Q$ is true, and $P$ is true, then $Q$ must be true.
-   **Template**: `SYLLOGISM` or `MODUS_PONENS`
-   **Usage**: Establishing consequence.
-   **Example**: "If it is raining (P), the ground is wet (Q)." -> Assert P ("It is raining") -> System confirms Q ("Ground is wet").

### 2. Modus Tollens (Denying the Consequent)
**Logic**: If $P \implies Q$ is true, and $Q$ is False, then $P$ must be False.
-   **Template**: `MODUS_TOLLENS`
-   **Usage**: Debugging or Falsification.
-   **Example**: "If the server is running (P), port 80 is open (Q)." -> Assert NOT Q ("Port 80 is closed") -> System infers NOT P ("Server is not running").

### 3. Disjunctive Syllogism (Exclusion)
**Logic**: Either $P$ or $Q$ is true. If $P$ is False, $Q$ must be True.
-   **Template**: `DISJUNCTIVE_SYLLOGISM`
-   **Reference**: $P \lor Q, \neg P \vdash Q$
-   **Usage**: Process of elimination.
-   **Example**: "The issue is Network (P) or Disk (Q)." -> Assert NOT Network -> System infers Disk.

### 4. Constructive Dilemma
**Logic**: $(P \implies Q) \land (R \implies S) \land (P \lor R) \vdash (Q \lor S)$
-   **Template**: `CONSTRUCTIVE_DILEMMA`
-   **Usage**: Mapping multiple possibilities to multiple outcomes.

### 5. Categorical & Causal Arguments
-   **DEFINITIONAL_ARGUMENT**: `Category(x) <- Feature(x)`. "If it has wings, it is a bird."
-   **CAUSAL_ARGUMENT**: `Effect(x) <- Cause(x)`. "If high load, then latency spike."
-   **EVALUATIVE_ARGUMENT**: `Good(x) <- Criteria(x)`. "If latency < 10ms, then Performance is Good."

### 6. Recursive Logic (Advanced)
You can define transitive relationships manually using `/assert/rule`.
-   **Transitivity**: `Path(?a, ?c) <- Link(?a, ?b), Path(?b, ?c)`
-   **Power**: This allows finding connections across infinite graph depths (Chain of Reasoning).

## Part 4: API Reference & Examples

### Base URL: `http://localhost:9300`

### 1. Asserting Knowledge (`POST /assert/fact`)
Teach the system about the current state of the world.

**Request**:
```json
{
  "predicate": "User_Role",
  "args": ["john_doe", "admin"],
  "scope": "prod_env"
}
```

**Response**: `Fact Asserted: User_Role(john_doe, admin)`

### 2. Asserting Rules (`POST /assert/rule`)
Teach the system how to think.

**Request (Defining "Access_Allowed" logic)**:
```json
{
  "head": { "predicate": "Access_Allowed", "args": ["?user", "?resource"] },
  "body": [
    { "predicate": "User_Role", "args": ["?user", "admin"] },
    { "predicate": "Resource_Type", "args": ["?resource", "sensitive"] }
  ],
  "scope": "prod_env"
}
```

### 3. Asking Questions (`POST /infer`)
Query the system. Use variables (`?x`) to find unknowns, or literals to check boolean truth.

**Query 1: "Is john_doe allowed to access the payroll DB?"**
```json
{
  "predicate": "Access_Allowed",
  "args": ["john_doe", "payroll_db"],
  "scope": "prod_env"
}
```
*Note: The system will stick to the constraints of `prod_env`. It will use the Rule defined above + the Fact defined in step 1 + needing to know if payroll_db is sensitive.*

**Query 2: "Who are all the admins?"**
```json
{
  "predicate": "User_Role",
  "args": ["?who", "admin"]
}
```
**Response**: `["User_Role(john_doe, admin)"]`

### 4. Transactions (`Atomic Operations`)
Use this when you need consistency (e.g., moving money, changing game turns).

1.  `POST /tx/begin` -> Returns `1001`
2.  `POST /assert/fact` (Header `X-Transaction-ID: 1001`) -> Buffer changes.
3.  `POST /assert/fact` (Header `X-Transaction-ID: 1001`) ...
4.  If anything looks wrong: `POST /tx/rollback/1001`
5.  If all good: `POST /tx/commit/1001`

### 5. Multi-Tenancy
Isolate your implementation plans or different user sessions.
-   Header `X-Database`: "my_game_db"
-   Header `X-Tenant-ID`: "player_session_55"
-   **Note**: Data in one tenant is *invisible* to another. Use this to run parallel simulations with different initial conditions.
